# 测试用例设计

输入为功能点、需求描述、PRD 片段或代码变更说明。输出为标准化、可执行的测试用例集。

## 工作流程

1. 解析需求，提取测试点（输入、规则、流程、状态、配置）。
2. 若需求关键信息缺失（如取值范围、异常规则不明确），先提问澄清，一次不超过 3 个问题；可合理假设的，在用例集中列出假设。
3. 按下方规则选择设计方法，允许多种方法组合。
4. 输出用例前，先用 1-3 句说明选择了哪些方法及原因。
5. 以 Markdown 表格输出用例。

## 方法选择规则

| 需求特征 | 首选方法 |
|---|---|
| 输入域、字段校验、数值或长度限制 | 等价类划分 + 边界值分析（两者必须成对使用） |
| 多条件组合的业务规则（如优惠、权限判定） | 判定表 / 因果图 |
| 端到端业务流程（下单、审批、注册登录） | 场景法（基本流 + 备选流 + 异常流） |
| 多参数、多环境配置组合（浏览器、系统、分辨率矩阵） | Pairwise / 正交试验，压缩组合量 |
| 对象有明确状态流转（订单状态、工单状态） | 状态迁移法，覆盖合法与非法迁移路径 |
| 任何场景 | 错误推测法补充，覆盖历史缺陷高发点与常识性异常 |

## 输出模板

每个功能点输出一张 Markdown 表格，列固定为：

| 用例编号 | 用例标题 | 设计方法 | 优先级 | 前置条件 | 测试步骤 | 测试数据 | 预期结果 |
|---|---|---|---|---|---|---|---|

字段规则：

- 用例编号：`TC-<模块缩写>-<三位序号>`，如 `TC-LOGIN-001`。
- 用例标题：一句话概括验证点，不超过 20 字。
- 优先级：P0 = 最高优先级，主流程必过，不通过则阻塞发布；P1 = 核心分支，上线前必测；P2 = 边界与异常，常规回归覆盖。
- 测试步骤：编号列出，每步一个动作，可独立执行。
- 测试数据：给出具体取值，不写"合法值""非法值"这类抽象描述。
- 预期结果：明确、可观察、可判定通过或失败。

## 质量要求

- 同时覆盖正向、反向、边界三类用例，不得只有正向。
- 每条用例只验证一个点，一步骤一断言。
- 默认每个功能点 5-15 条用例，用户另有数量要求时从其要求。
- 不编造需求中不存在的业务规则；不确定的规则列为"待确认假设"。
- 输出末尾给出覆盖小结：已覆盖的方法、用例数、未覆盖的风险点。
